## Blocking

### B1, colliding media keys can substitute one DOCX image for another

`crates/rdocx-layout/src/engine.rs:154`
`crates/oxml-layout/src/output.rs:64`
`crates/rdocx-layout/src/paginator.rs:310`

F-046 collects every relationship-resolved image into a single
`HashMap<MediaId, ImageData>`. That collection overwrites an earlier entry when
two different byte sequences produce the same `MediaId`, even though the shared
type explicitly says the compact FNV-1a key is not collision-free. Both inline
and anchored images then recover their bytes only through that key, so every
element in the collided bucket receives whichever image survived collection.
Before this cutover, the retained Word engine resolved bytes by relationship ID,
so this changes rendered output for a valid document containing colliding media.
A fix must keep distinct bytes addressable when their compact media keys collide
and must cover both inline and anchored image resolution with a forced-collision
regression.

## Should-fix

### S1, migration notes omit breaking retained-layout APIs

`CHANGELOG.md:44`
`crates/rdocx-layout/src/paginator.rs:83`
`crates/rdocx-layout/src/block.rs:36`
`crates/rdocx-layout/src/block.rs:145`

The breaking-change section documents the removed `line` module and the shared
output structures, but it does not name several breaking changes in retained
public `rdocx-layout` APIs. `paginate_sections` now requires a media map,
`AnchoredContent::Image` replaces `embed_id: String` with `media_id: MediaId`,
and `ParagraphBlock::jc` replaces `Option<ST_Jc>` with `Option<Align>`. This
falls short of F-051's promise to document all intentional breaking surfaces.
The migration notes should name these changes and give downstream callers the
new types or call shape.
